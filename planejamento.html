Sistema de gestão patrimonial e imobiliária da holding familiar

Django + Unfold Neon Postgres Cloudflare R2 Railway Custo alvo: US$ 0/mês

Visão geral

Sistema de uso interno familiar para gestão centralizada de patrimônio imobiliário. Cobre contratos, imóveis, inquilinos, documentos, prazos e relatórios para IR.

O responsável reside em Toronto (UTC-5), portanto o sistema precisa operar de forma autônoma e de baixíssima manutenção. Uma administradora local cuida do dia-a-dia operacional; o sistema cobre a camada estratégica.

Princípios norteadores

Baixa manutenção > otimização
Aproveitar Django Admin + Unfold ao invés de criar UI customizada. Toda operação interna roda no admin.
Custo zero
Toda a stack escolhida tem free tier suficiente para o volume familiar. Crédito mensal de US$ 5 da Railway absorve o app.
Auditabilidade
Histórico de alterações em entidades críticas (contratos, imóveis, pagamentos). Soft delete em pessoas. Exigência de IR.
Operação remota-first
Todos os prazos críticos disparam alertas automáticos. Nada depende de o responsável "lembrar" de algo.

Fluxo de requisições (web)

  1. Usuário acessa o admin Django via HTTPS na Railway.
  2. Django autentica via sessão padrão; Unfold renderiza o admin.
  3. Leituras/escritas de dados estruturados → Neon Postgres via psycopg.
  4. Uploads de documentos → R2 via django-storages (S3-compatible). URLs assinadas para download privado.

Fluxo de tarefas agendadas

  1. Railway cron job dispara python manage.py <comando> em horários definidos.
  2. Comando lê prazos (contratos vencendo, IPTU, seguro-fiança, reajustes) do Postgres.
  3. Sistema gera Tarefa/Lembrete e/ou dispara notificação (e-mail).

Infraestrutura

Railway · App
  • Deploy: git push → build automático
  • Crédito mensal: US$ 5 (suficiente para 1 serviço web + crons)
  • Sem cold start (compatível com Django sem ajustes)
  • Variáveis: DATABASE_URL, R2_*, SECRET_KEY, ALLOWED_HOSTS
Neon · Postgres
  • Free tier ou Launch (avaliar conforme uso)
  • Backup: PITR de 7 dias incluso
  • Branching de banco para staging (opcional)
  • Conexão: DATABASE_URL via env
Cloudflare R2 · Storage
  • 10 GB grátis, zero egress
  • Compatível com S3 (boto3)
  • Backend: django-storages com S3Boto3Storage
  • Acesso a documentos via URL assinada (privacidade)
Railway · Cron jobs
  • Cada lembrete = 1 cron chamando 1 management command
  • Frequência típica: diária às 09:00 BRT
  • Ex.: manage.py verificar_contratos_vencendo

Apps e Models

Estrutura Django

plataforma_mb/
├── pessoas/        # Pessoa + Perfis (Party pattern)
├── imoveis/        # Imovel, ImovelProprietario
├── contratos/      # Contrato, Garantia
├── documentos/     # Documento (GenericForeignKey)
├── financeiro/     # [Backlog] Pagamento, Despesa, IPTU
└── core/           # Tarefa, Lembrete, base abstratas

App: pessoas ✅

Pessoa
  • id PK
  • nome, apelido CharField
  • cpf_cnpj CharField unique=True — persiste só dígitos (11=CPF, 14=CNPJ)
  • tipo TextChoices (PF, PJ)
  • email, telefone, endereço
  • ativo BooleanField (soft delete)
PerfilProprietario
  • pessoa OneToOneField → Pessoa (PROTECT)
  • interno BooleanField — distingue membros da família/holding de terceiros
PerfilCliente / PerfilImobiliaria / PerfilFiador
  • pessoa OneToOneField → Pessoa (PROTECT)
  • + campos específicos do papel (profissão, renda, CRECI, contato responsável)

App: imoveis ✅

Imovel
  • id PK
  • nome, tipo — TextChoices
  • status TextChoices (DI/AL/VE/RE/IN/GT) — GT = Gerido por terceiros
  • endereco, complemento, bairro, cidade, estado, cep
  • area_total, quartos, vagas
  • valor_mercado, matricula
  • @property valor_por_m2 — valor_mercado / area_total
  • @property participacao_interna_pct — soma participações com interno=True
  • @property valor_interno — valor_mercado × participacao_interna_pct
  • + HistoricalRecords (django-simple-history)
ImovelProprietario (through)
  • imovel FK → Imovel (PROTECT)
  • proprietario FK → PerfilProprietario (PROTECT)
  • participacao Decimal (0..1) — clean() valida soma ≤ 1

App: contratos ✅

Contrato
  • imovel FK → Imovel (PROTECT)
  • cliente FK → PerfilCliente (PROTECT)
  • imobiliaria FK → PerfilImobiliaria (PROTECT, null)
  • data_inicio Date
  • vigencia IntegerField — duração em meses
  • renovacao_automatica BooleanField
  • quant_renov_automaticas PositiveSmallIntegerField
  • valor_aluguel Decimal
  • indice_reajuste TextChoices (IGPM, IPCA, INCC, FIXO, OUTRO)
  • dia_vencimento PositiveSmallIntegerField (1–28)
  • rescindido_em Date (null)
  • @property data_fim — data_inicio + vigencia × (1 + renovações) via add_months
  • @property status — Futuro / Ativo / Renovado / Vencido / Rescindido
  • @property historico_precos — lista de períodos com valor e datas, via HistoricalRecords
  • + HistoricalRecords (django-simple-history)
Garantia
  • contrato FK → Contrato (CASCADE)
  • tipo TextChoices (FIADOR, DEPOSITO, SEGURO, SEM_GARANTIA)
  • fiador FK → PerfilFiador (null, PROTECT) — obrigatório se tipo=FIADOR
  • valor Decimal (null) — depósito, seguro ou título

App: documentos

Documento
  • arquivo FileField (R2 via django-storages)
  • tipo TextChoices (matricula, contrato, comprovante, laudo, escritura, procuracao, seguro)
  • vencimento Date (null)
  • content_type, object_id, content_object GenericForeignKey

App: core (transversal)

Tarefa / Lembrete
  • titulo, descricao, vencimento
  • recorrencia TextChoices (anual, mensal, unica)
  • tipo (reajuste, renovacao, iptu, seguro, irpf, manual)
  • concluida BooleanField
  • content_type, object_id GenericForeignKey

Padrões obrigatórios

  • on_delete=PROTECT em todas as FKs de perfis (auditoria/IR)
  • Soft delete em Pessoa via ativo — nunca delete físico
  • Campos calculados sempre @property, nunca persistidos
  • Enums via TextChoices, nunca model separada
  • Histórico em Contrato, Imovel, Pagamento via django-simple-history
  • FKs apontam para Perfil, nunca para Pessoa direto

Cardinalidades-chave

RelaçãoCardinalidadeon_delete
Pessoa → Perfil*1 : 0..N (um por papel)PROTECT — impede deleção de Pessoa com histórico
Imovel ↔ PerfilProprietarioN : N (via ImovelProprietario)PROTECT
Contrato → ImovelN : 1PROTECT
Contrato → PerfilClienteN : 1PROTECT
Contrato → PerfilImobiliariaN : 0..1PROTECT
Contrato ↔ Garantia1 : 0..NCASCADE
Garantia → PerfilFiadorN : 0..1PROTECT
Documento → *N : 1 (GenericForeignKey)n/a (Generic)

Invariantes

  • Pessoa.cpf_cnpj único — chave natural anti-duplicidade
  • Σ ImovelProprietario.participacao por imovel ≤ 1.0 (validado em clean() — validação exata = 1 no backlog)
  • Pessoa com qualquer histórico → nunca deletar (PROTECT em todas as FKs de perfil)
  • Reajuste e vencimento sempre populados em Contrato ativo (lembretes dependem disso)

Lembretes & Crons

Toda automação roda como Railway cron job chamando um Django management command. Sem Celery, sem fila — volume não justifica.

Padrão de implementação

# core/management/commands/verificar_contratos_vencendo.py
from django.core.management.base import BaseCommand
from datetime import date, timedelta
from contratos.models import Contrato
from core.models import Tarefa

class Command(BaseCommand):
    def handle(self, *args, **opts):
        alvo = date.today() + timedelta(days=60)
        for c in Contrato.objects.filter(rescindido_em__isnull=True):
            if c.data_fim == alvo:
                Tarefa.objects.get_or_create(
                    content_object=c,
                    tipo="renovacao",
                    defaults={"titulo": f"Renovar contrato {c}", "vencimento": c.data_fim}
                )

Roadmap MVP

Fase 0 — Setup (1-2 dias)

  • Criar projeto Django + virtualenv + requirements.txt
  • Configurar Unfold como admin
  • Conectar Neon Postgres via DATABASE_URL
  • Configurar django-storages com R2
  • Criar conta Railway, conectar repo, primeiro deploy
  • Configurar variáveis de ambiente

Fase 1 — Pessoas (PES) (2-3 dias)

  • Model Pessoa com cpf_cnpj único (persiste só dígitos; máscara CPF/CNPJ no widget)
  • Models Perfil* (4 perfis MVP: Proprietário, Cliente, Imobiliária, Fiador) com OneToOne
  • Admin: PessoaAdmin com inlines + admins próprios por perfil
  • Soft delete via ativo; filtros no admin

Fase 2 — Imóveis (PAT) (2-3 dias)

  • Model Imovel + ImovelProprietario through
  • Validação clean() de soma de participações ≤ 1 (validação = 1 no backlog)
  • @property calculadas: valor_por_m2, participacao_interna_pct, valor_interno
  • Filtros por situação/tipo/estado no admin
  • django-simple-history em Imovel

Fase 3 — Contratos (CON) (3-4 dias)

  • Models Contrato + Garantia
  • Histórico de auditoria (django-simple-history)
  • Status calculado: Futuro / Ativo / Renovado / Vencido / Rescindido
  • Admin com inline de garantias, displays formatados e histórico de preços
  • Custom action: calcular reajuste IGPM/IPCA → backlog
  • Custom action: gerar recibo PDF → backlog

Fase 4 — Documentos (DOC) (1-2 dias)

  • Model Documento com GenericForeignKey
  • Upload para R2 funcionando
  • URLs assinadas para download
  • Inline no admin de imóvel/contrato/pessoa

Fase 5 — Lembretes (LEM) (2-3 dias)

  • Model Tarefa com GenericFK
  • Management commands (6 lembretes)
  • Configurar Railway crons
  • Envio de e-mail simples via SMTP

Fase 6 — Relatórios (REL) (2-3 dias)

  • Custom action: relatório patrimonial consolidado
  • Custom action: rendimentos por CPF (export para IR)
  • DRE simplificado por imóvel
